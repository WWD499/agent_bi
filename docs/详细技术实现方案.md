## 一、总体技术架构

### 1.1 分层架构

系统采用五层架构设计，自上而下依次为：

![系统分层架构图](分层架构图.png)

| 层次 | 组成模块 | 职责说明 |
|------|----------|----------|
| **前端交互层** | 界面工程（页面框架 + 构建工具 + 组件库 + 图表库）<br>令牌认证 / 流式读取（事件流） | 提供用户对话界面；管理登录态；实时接收并渲染推理过程和结果 |
| **接入网关层** | 登录控制器 / 对话控制器 / 令牌配置 | 处理用户登录鉴权；接收对话请求并建立推送通道；配置令牌校验规则 |
| **智能体编排层** | 智能体主服务（手写推理循环）<br>会话管理 / 记忆管理 / 工具接口注册 | **系统核心**——驱动"思考→调用工具→观察→再思考"的推理循环；管理多轮会话上下文；注册和调度全部业务工具 |
| **业务服务层** | 查询服务 / 知识服务 / 预警服务<br>数据源服务 / 数据源工厂 / 图表选型器 | 封装各类业务能力：自然语言转查询、知识库检索、预警分析、动态数据源连接、图表自动选型 |
| **基础设施层** | 大模型调用服务 / 安全校验器 / 向量检索引擎 | 底层能力支撑：与大模型网关通信、查询语句五层安全校验、向量语义相似度计算 |

**数据存储（底层）**：

| 存储角色 | 数据库类型 | 存储内容 |
|----------|-----------|----------|
| 系统库 + 向量库 | PostgreSQL（含向量扩展） | 用户权限、平台元数据、数据源配置、知识库条目及向量索引 |
| 业务数据源 | MySQL（动态对接） | 实际业务数据（订单、客户、产品、营收等），通过配置表按需接入 |

### 1.3 关键技术决策：为何弃用 Spring AI 框架

- **问题暴露**：项目初期规划使用 Spring AI 作为智能体编排框架。但在本机环境实测时发现，Spring AI 1.0.0 正式版的依赖包中**缺失多个核心类**（对话客户端/工具回调/消息封装等），模块拆分存在异常。
- **最终决策**：放弃 Spring AI 框架依赖，改为基于已验证的大模型调用服务（OpenAI 兼容协议 + 原生函数调用 + 流式输出），**手写 ReAct 推理循环**。
- **收益分析**：零新增外部依赖、零网络版本风险、对工具调用协议完全可控、调试过程透明。
- **代价评估**：需自行实现函数调用解析/上下文回填/步数上限控制等逻辑，但逻辑集中且代码量可控（约 200 行）。

## 二、核心技术实现原理

### 2.1 手写 ReAct 推理循环（智能体主服务）

这是系统的**核心调度引擎**，负责驱动整个"思考→行动→观察→再思考"的循环。

#### 实现逻辑（伪代码描述）

```
初始化：
  加载该会话的历史记忆消息列表
  将用户的新问题追加到消息列表中

循环（最多重复 15 次）：
  步骤1 — 调用大模型：
    将「消息列表 + 十五项工具的能力描述」发送给大模型
    请求大模型判断下一步该做什么

  步骤2 — 解析模型返回的决策：

    如果决策是「调用某个工具」：
      a. 通过流式推送通知前端："正在调用XX工具"
      b. 根据工具名称将请求分发给对应的工具执行器
      c. 工具执行完毕后获取结果
      d. 通过流式推送通知前端："工具返回了XX结果"
      e. 将「模型的工具调用指令」和「工具的实际返回结果」
         分别作为两条消息回填到上下文列表中
      f. 回到步骤1，继续下一轮推理

    如果决策是「可以直接回答用户了」：
      a. 请求大模型以流式模式生成最终答案
      b. 每收到一段文本片段，立即通过流式推送前端逐字显示
      c. 全部生成完成后推送"结束"标记
      d. 退出循环，本次对话结束

循环正常结束（未在第15步内给出答案）：
  基于已有的所有中间结果，让大模型生成一个兜底摘要推送给用户
```

#### 关键设计细节

| 设计点 | 实现方式 | 目的 |
|--------|----------|------|
| 工具能力描述 | 每个工具提供结构化的能力声明（名称/功能说明/参数定义），启动时组装成清单随请求发给模型 | 让大模型理解每个工具能做什么、需要什么参数 |
| 上下文回填协议 | 模型决定调用工具时，记录"调用了哪个工具"；工具返回后，记录"工具返回了什么"。两条消息按顺序加入对话历史 | 让大模型在下一轮能看到自己之前做了什么、得到了什么 |
| 异步执行 | 推理循环运行在虚拟线程上；接口收到请求后立即返回推送通道对象，不阻塞请求线程 | 支持多用户并发对话 |

### 2.2 大模型调用服务（双模式）

系统通过统一的调用服务与大模型网关通信，提供两种工作模式：

**模式一：结构化调用**
- 用途：推理循环中需要模型做出"调用工具还是直接回答"的决策时
- 工作方式：发送完整的对话上下文 + 工具能力清单 → 等待模型返回完整响应 → 解析响应中的函数调用指令
- 适用场景：ReAct 循环的每一步决策

**模式二：流式生成**
- 用途：模型确定可以给出最终答案后，生成答案文本时
- 工作方式：发送上下文 → 开启流式模式 → 模型每生成一段文本就推送过来 → 逐段转发给前端 → 收到结束标记后停止
- 适用场景：最终答案的打字机效果展示

**模型与网关**：通过统一 OpenAI 兼容网关 `https://ai-api-prod.qingjiao.art/v1` 接入，对话模型 deepseek-v3、向量化模型 BAAI/bge-m3（1024 维）；API 密钥经环境变量 ARK_API_KEY 传入，不落盘。

**身份验证**：通过请求头携带 API 密钥进行鉴权。密钥仅存储于服务器运行时的环境变量中，不写入任何配置文件或数据库。

### 2.3 工具接口规范

所有业务工具遵循统一的接口契约：

| 接口方法 | 说明 |
|----------|------|
| 工具名称 | 唯一标识符，供模型识别和调度 |
| 功能描述 | 自然语言描述，告诉模型这个工具是做什么用的 |
| 参数声明 | 结构化的参数定义（参数名/类型/是否必填/说明），供模型生成正确的调用参数 |
| 执行方法 | 接收模型生成的参数JSON，执行具体业务逻辑并返回结果文本 |

**扩展方式**：新增工具只需实现上述四个方法并在主服务中注册即可，无需修改其他模块。

### 2.4 写工具确认与自我修正

沙箱写工具（建表 / 改名改表 / 数据源导入 / CTAS 落表 / 删表）在工具定义中标记 `requiresConfirmation=true`。当 Agent 调度这些写工具时，执行前先 emit `confirm` 事件将流程挂起，前端弹出确认框由用户决策：

- **用户同意**：才真正执行写操作、落库生效；
- **用户拒绝**：Agent 自动降级为只读方案，仅基于已有数据给出分析，不执行任何写入。

写工具在执行失败时支持**自我修正循环**：自动分析失败原因并调整参数后重试，最多重试 3 次；仍失败则如实返回错误，由兜底摘要机制接管。

### 2.5 RAG 知识库检索

#### 向量化存储

- 使用 BAAI/bge-m3 嵌入模型（输出 1024 维向量），与数据库向量字段维度精确匹配
- 知识条目入库时，将其正文内容通过嵌入模型转换为向量，存入向量字段
- 曾因误选 4096 维嵌入模型导致维度不匹配无法入库，已修正为 1024 维

#### 语义检索流程

```
用户提问 → 将问题文本转为向量 → 在知识库中计算余弦相似度排序
                                ↓
                    同时执行关键词模糊匹配（兜底保障）
                                ↓
                    合并两组结果去重 → 按综合评分返回 Top-K 条目
```

**混合检索策略**：当嵌入模型暂时不可用时，关键词匹配通道仍可独立工作，保证检索服务不会完全失效。

### 2.6 自然语言转查询（NL2SQL）

#### 处理流水线

```
用户自然语言问题
       ↓
① 业务术语消解（调用知识库检索相关口径定义）
       ↓
② 结合术语含义 + 数据库表结构信息 → 生成查询语句
       ↓
③ 自动执行查询语句
       ↓
④ 分析返回数据的特征（几列、什么类型、多少行、是否有时间趋势…）
       ↓
⑤ 匹配最适合的图表类型
       ↓
⑥ 截取前20条样本数据
       ↓
⑦ 让大模型对数据进行解读分析（发现了什么趋势、异常点…）
       ↓
⑧ 整合以上全部内容作为统一结果返回
```

#### 图表选型逻辑

根据数据特征的自动匹配规则：

| 数据特征判断条件 | 选择图表类型 | 直观理解 |
|------------------|-------------|----------|
| 包含时间列 + 单个数值列 | 折线图 | 适合观察趋势变化 |
| 包含分类列 + 单个数值列 | 柱状图 | 适合比较大小高低 |
| 包含分类列 + 双数值列 | 组合图（柱+线） | 同时看数值和趋势 |
| 数值列之间有构成关系 | 饼图/环形图 | 适合看占比分布 |
| 维度超过3个或行列复杂 | 数据透视表格 | 适合多维交叉分析 |

图表选型器根据上述规则自动判断，同时生成前端可直接使用的图表配置数据。

#### 中文表名解析

业务库存在中文表名时，`list_tables` 工具直接返回中文 `tableName`；模型生成 SQL 时以 `sandbox."中文表"`（带引号、前缀 `sandbox.`）的方式引用。表名重写正则已支持中文表名（含引号写法），可正确将模型写出的中文短名映射回物理表。这一机制解决了模型按中文短名写 SQL 时「找不到物理表」的问题，使中文表名的取数与分析链路闭环。

### 2.7 只读安全执行

#### 五层防护的执行顺序

```
用户提交的原始查询语句
       ↓
第1层检查：语句必须以 SELECT 或 WITH 开头？ ──否→ 拒绝
       ↓ （通过）
第2层检查：语句中不含 INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE？ ──含→ 拒绝
       ↓ （通过）
第3层检查：不含注入攻击特征模式（注释拼接/恒真条件/联合查询等）？ ──含→ 拒绝
       ↓ （通过）
第4层检查：不含分号分隔的多段语句？ ──含→ 拒绝
       ↓ （通过）
第5层检查：引用的所有表名都在白名单范围内？ ──不在→ 拒绝
       ↓ （全部通过）
动态连接目标数据库执行查询 → 返回结果（限制最多100行）
```

#### 动态数据源连接

- 系统不硬编码任何业务数据库连接信息
- 所有业务数据源的连接参数（地址/端口/库名/账号/加密密码）均存储在系统配置表中
- 执行查询时，根据指定的数据源编号从配置表中读取参数，即时建立数据库连接
- 查询结束后连接释放，不做持久化保持

### 2.8 身份鉴权机制

#### 鉴权流程

```
用户提交账号密码 → 服务端校验 → 校验通过则创建登录会话 → 颁发访问令牌
                                                              ↓
后续每次请求携带令牌 ← 前端保存令牌到本地存储 ← 返回令牌给前端
       ↓
全局拦截器检查令牌有效性 ── 有效 → 放行进入业务处理
                       ── 无效 → 返回401未授权错误
```

**历史问题记录**：曾因令牌头名称配置为 `Authorization`（标准Bearer格式），而前端又手动拼接了 `Bearer` 前缀，导致系统将 `Bearer xxx` 整串当作令牌解析而验证失败，全接口返回 401。修复方式：将令牌头改为自定义名称 `satoken`，前端直接传令牌值不加前缀。

## 四、安全设计总览

| 风险类别 | 具体风险 | 防护措施 |
|----------|----------|----------|
| 数据安全 | SQL 注入攻击导致数据泄露或篡改 | 五层安全校验 + 表名白名单 + 仅开放只读查询 |
| 数据安全 | 越权写入或删除数据 | 工具层面不暴露任何写操作能力 |
| 运行安全 | 工具调用陷入无限循环 | 单轮严格限制 15 次调用上限 |
| 运行安全 | AI 服务密钥泄露 | 密钥仅存于运行环境变量，不落盘 |
| 访问安全 | 未授权访问业务接口 | 全局拦截器覆盖所有业务路径 |
| 可用性 | LLM 服务超时或不可用 | 异常捕获 → 推送友好错误信息 + AI 兜底摘要 |
| 可用性 | 模型幻觉导致危险操作意图 | 即使模型生成了危险意图，五层防护也会在执行阶段拦截 |
